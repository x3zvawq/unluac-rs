# 测试体系

本文定义仓库的公开测试协议、运行方式和失败分类。具体回归问题由最小源码 case 与实现注释记录，
不在设计文档维护 case 流水账。

## 源码分类与索引

| 层次 | 路径 / 入口 | 责任 |
| --- | --- | --- |
| 源码合同 | `tests/case_<type>/<subtopic>_<编号>_<title>.lua` | 基础语义、已知问题、方言与可读性使用同一验证协议 |
| 驱动器 | `xtask/src/case_test.rs` | 主分类/标签筛选、索引导出、并发、超时和汇总 |
| 支持库 | `packages/unluac-test-support/` | toolchain、manifest、验证与 diff |

主分类决定文件归属，一个源码可以拥有多个交叉主题标签；不再区分 unit/regression suite。
文件使用子主题、两位编号和具体标题，格式为 `case_<type>/<subtype>_<NN>_<title>.lua`。
编号从 `01` 开始，在每个 `(type, subtype)` 组内独立分配；同组编号不得重复，不同组可重复。
文件名排序先聚拢子主题，再按补零编号排列。子主题描述稳定的语义边界；方言、优化档与
safe/unsafe 等差异通过配置、标题或 tags 表达，不各自切出大量一次性的子主题。
新增取本组现存最大编号加一；合并/删除留下的空号不补齐，旧文件不因插入新例而重排。
编号仅用于组内排序，定位仍使用完整路径和 tags；不能把它与 runner 的展开实例 ID 混用。
例如 `case_calls/method_01_receiver_single_value.lua` 与 `method_10_call_updates.lua`
属于同一组，而 `case_calls/callee_01_short_circuit_header_call.lua` 独立从 `01` 编号。
主分类为 `control_flow`、`calls`、`tables`、`closures`、`lifetime`、`literals`、`operators`、
`bindings`、`syntax`、`protocol`、`stress`、`runtime`。

manifest 按主分类声明每份源码一次：路径、多个标签、一句保护边界和配置数组属于同一源码定义。
方言、debug、优化档、expectation、结构合同和收敛预算属于配置；同一源码的不同配置不得因合并
文件或去重展示标签而丢失。标签用于召回相关样例，不能单独证明覆盖包含关系。
新增样例前先按分类和标签检索，优先补充现有主题的独立子场景；只有已有载体无法保留目标边界时
再增加文件。依赖常量宽度、局部槽、捕获关系或最小 CFG 的样例，合并时必须保留实际编译载体。

`cargo case-test --list` 按源码列出筛选后的配置数量、标签和断言统计；`--list-json` 在每份源码下
嵌入完整实例数组（含 ID 和展开配置），均不运行 Lua。断言统计复用 selector 校验时的单次源码解析，
属于整份源码的指令库存，不表示当前筛选实例必然执行每条指令，也不表示运行路径覆盖率。
`--type` 筛选主分类；重复 `--tag` 要求全部标签匹配；重复 `--case-filter` 在路径、保护边界、标签和
variant 展示名中按子串 OR 匹配。运行配置以 manifest 为准，不另用 `all-dialects` 等静态标签复制矩阵。
`--report-json <path>` 记录本次执行的配置、结果、失败详情与每个实例耗时，总耗时不含构建及索引。
实例耗时覆盖子进程执行与结果收集，不能视为单个反编译 pass 的耗时；并发实例耗时之和也不等于墙钟时间。
普通 Source 产物在可读性检查之前落盘，首次生成及后续轮次的形状合同失败也保留实际源码，便于按失败批次审阅。

### 信息归属

| 信息 | 唯一维护位置 | 获取方式 |
| --- | --- | --- |
| 主分类、子主题和组内编号 | Lua 源码路径 | 文件列表或 `rg --files tests` |
| 交叉标签、保护目的、配置矩阵 | `case_manifest/` 中的源码定义 | `cargo case-test --list` / `--list-json` |
| 可读性合同、外部运行观察 | Lua 内的 `unluac:` / `unluac-runtime:` 注释 | 直接阅读或 `rg`，runner 按协议解析 |
| 语义观察 | Lua 实际执行的断言与输出 | 运行样例；不能由元数据推断覆盖 |
| 当前执行结果 | 本次 runner 输出和 `--report-json` 产物 | 按本次报告定位失败 |

不手工维护上述信息的第二份 JSON 清单。旧路径对应、迁移处理决定和历史验证结果不属于测试合同，
不复制进设计文档或样例文件头。样例注释解释所保护的行为，断言固定预期；标签与目的目前仍由
manifest 提供，普通说明性注释不会自动进入索引。

例如只需检查源码断言库存时可直接检索：

```sh
rg -n '^-- unluac:|^-- unluac-runtime:' tests
```

各 crate 的 `src/`（含 CLI、WASM 和 xtask）只保留实现，不放 `#[cfg(test)]`、`#[test]` 或同目录
Rust 测试模块；新增测试统一使用 Lua 样例。公开 case 必须是仓库官方
Lua toolchain 可编译的源码，不接受只提交 `.luac` / `.luau` 的 bytecode-only fixture。

## 验证流水线

```text
source execution
  -> official compile
  -> bytecode execution vs source
  -> decompile
  -> generated source compile + execution vs source
  -> optional recompile/decompile rounds
  -> semantic, source-kind, convergence and readability assertions
```

普通 case 必须覆盖真实用户路径。少数无法由普通小源码稳定产出的 VM 协议或宽度边界，可以由
manifest expectation 使用 pinned 官方 runtime 动态构造临时 chunk，但源码 baseline 仍必须存在；
临时 chunk 不提交到仓库，也不能成为 runner 内的 case 特判。

目标 Lua 源码确实无法等价表达的 VM carrier 可以声明 typed residual expectation。它必须绑定
精确不可表达性证明和最小源码入口，Strict 返回对应 residual，Permissive 返回同类
`DiagnosticPseudocode`；不得用 residual 掩盖可修复的 lowering 或 pass 证明缺口。

## 运行命令

Luau 的源码基线使用配置中的优化档；原 chunk、首次生成及每轮回编译的 chunk
都由 `luau-bytecode-runner` 实际执行。源码与二进制 runtime 的选择属于 toolchain，
不按扩展名猜测，也不把重新解释执行源码当作已执行编译产物。GC 观察入口与 pinned
CLI 保持一致；编译配置引起的求值顺序差异须在同一配置的完整输出比较中核对。

### 按改动选择验证

- 纯文档、注释或技能指令修改：检查路径、链接、示例与实际入口是否一致，以及 `git diff --check`；SKILL 修改另检查 frontmatter 和触发范围。无需启动 Lua 全矩阵或 Rust 构建。
- Rust 修改：先运行能暴露当前问题的定向测试；交付前运行 `cargo clippy --workspace --all-targets --all-features --locked -- -D warnings`。反编译行为、语义合同或共享流水线变化，还需在完整主题收尾时运行一次 `cargo case-test --jobs 8`，jobs 按可用资源调整，不要求每个编辑步骤重复全量。
- runner、CLI、WASM、JS 或 Web 的专项修改：运行对应包已有检查并覆盖实际受影响入口；跨入口影响再扩大范围。核心 API、feature 或依赖变化涉及 WASM 时验证相应构建目标。发布流程所要求的全量检查仍以工作流为准。
- case / manifest 修改：通过 `cargo case-test --case-filter <case>` 验证注册后的实际实例与适用方言；测试协议或共享执行逻辑变化时扩大到受影响主题。

已通过且未再受改动影响的检查不重复运行。出现新改动、新失败或尚未解决的具体疑点时才追加
验证；无法执行必要检查时明确说明未验证部分，不能宣称全部完成。失败基线应来自可核对的当前
证据，不能引用旧记录中的通过数替代本次运行，也不能仅凭失败总数相同判断没有新回归。

### 命令示例

```sh
cargo case-test --jobs 8
cargo case-test --type calls --jobs 8
cargo case-test --type control_flow --jobs 8
cargo case-test --case-filter <path-or-variant>
cargo case-test --output verbose --case-filter <case>
cargo case-test --recompile-rounds 1
```

`cargo test --test regression` 和 `tests/regression/` 不是测试入口。

manifest 中显式 `recompile_rounds: Some(n)`（n > 0）是收敛预算：每轮先完成语义验证，
再比较相邻两轮生成源码，首次相同即成功。`None` 使用 runner 的全局再生成轮数并验证
每轮运行语义，但不因文本尚未固定而失败；默认一轮通过不能作为源码收敛证据。
显式收敛 case 从首次生成起关闭 Generate 的元信息注释，避免产物路径、行号变化造成假失败；
debug 信息仍参与解析和命名，普通 debug/注释 case 保留默认注释输出，不在比较器中删除源码文本。
每轮输入直接使用上一轮已经编译并执行验证的 chunk；同一 case 的方言、优化档与 debug
编译选项不变，不再复制上一轮源码到新路径重新编译。首次输入来自 `generated-chunk`，
后续输入来自前一轮的 `recompile-round-N-regen` 产物；保留真实源码路径及 debug 来源。
每份新生成源码仍独立落盘、编译、执行并与源码 baseline 比较，之后才判断文本固定或
传给下一轮。复用编译产物不跳过安全型可读性断言、运行观察器或任何新输出的验证。
语义所需的 Luau optimize pragma 即使关闭展示注释也保留，并参与源码收敛比较；runner
不剥除它或另行补写。原样例编译档与生成源码的显式编译要求分别按各自产物实际执行。
预算耗尽仍不固定则报告 convergence mismatch。不能通过增加轮数掩盖持续膨胀。只有明确的协议
压力 case 可以在 manifest 将其设为 `0`，且仍需完成首次生成、重编译与运行等价验证。

runner 路径必须消费同一次 Cargo build 的 `compiler-artifact.executable`，不得按默认
`target/debug`、环境变量或 profile 名重建。自定义 `CARGO_TARGET_DIR` 也必须启动刚构建的
同一产物；Cargo 未发布 executable 时直接报错，不能退回磁盘中的旧 runner。

manifest 将全部主题展开为单一矩阵并签发实例 ID，选项不同的条目拥有不同身份。
父驱动器从同一次构建的子 runner 列表获取 ID，并以 ID 选择完整条目；
path、dialect 和 variant 标签只用于展示与筛选，不能重新匹配条目而丢弃 debug、expectation 等事实。
普通产物路径为 `target/unluac-tests/cases/<dialect>/case-<id>/<stage>/<case-path>`，所有阶段直接消费同一条目。
ID 只对应当前编译的 manifest 展开顺序，不能跨清单版本保存或作为持久 case 标识。
直接调试 `case_runner` 时先使用 `--list`，再用 `--id <id>` 执行该实例。

每个 case 由独立子 runner 执行。子 runner 的 panic 或异常退出必须保留状态与 stderr，归类为
该 case 的 `runner-crashed` 失败后继续执行其余 case；spawn、poll、pipe 读取等驱动器基础设施
错误才终止整批测试，并立即取消尚未开始的任务。stdout/stderr 必须在子 runner 执行期间持续
读取，不能等进程退出后再读取有界 pipe。
Windows 超时必须在 runner 仍存活时按其 PID 终止整棵子进程树，再等待退出和收集输出；
只终止 runner 会留下 Lua 进程及其继承的 pipe，使超时处理自身无法结束。

进度输出必须同时适用于交互终端和日志型调用方：TTY 可以原地重绘当前 case，但每完成 100 个
entry 仍要通过进度渲染器写入一条不会被后续重绘覆盖的持久里程碑；距离上次持久进度输出连续
10 秒时，必须写入包含 completed/total 与 active 数量的持久心跳，即使期间 worker event 一直
到达。这样慢 case、低吞吐波次或终端重绘被宿主折叠时都不会表现为无进度挂死。
`--progress off` 必须同时关闭重绘、里程碑和心跳。

## Lua Case 规范

- 一个文件围绕同一主题，可包含多个带稳定输出标签的子 case。
- 源码路径的主分类和子主题描述实际保护边界，方言配置放在 manifest，不按历史来源区分测试等级。
- 回归源码必须最小化，避免复制大型真实文件或在 manifest 中重述实现细节。
- 同一源码的优化档位、命名模式或 debug 模式使用 manifest variant，不复制源码。
- 测试默认剥离 debug；只有协议或命名目标依赖 debug 时才显式 `retain_debug`。
- case、variant、expectation 的注册与执行顺序必须确定，不能依赖文件系统或 hash 顺序。
- 普通运行比较观察进程输出与退出状态，不观察 chunk 返回值。被测函数必须实际调用，结果须通过
  `assert` 或稳定输出观察；只定义/返回函数、只返回结果表不能充当对应行为的运行证据。
  无序遍历的结果应在观察端归一化；专用 expectation 则按其协议确认真实验证范围。

推荐用注释和输出首参标记子 case：

```lua
-- common_example#1: 多赋值保持求值顺序
local function test_assignment()
    local a, b = left(), right()
    print("common_example#1", a, b)
end

test_assignment()
```

## 外部运行观察

Luau 普通等价 case 可用 `-- unluac-runtime:` 注释行定义额外运行观察器。按文件顺序
连接冒号后的代码（可选一个空格会移除），形成独立 Lua chunk；它通过 `...` 接收
已加载的被测函数，必须实际调用该函数并用断言或稳定输出观察目标行为。例如：

```lua
-- unluac-runtime: local run = ...
-- unluac-runtime: local calls = 0
-- unluac-runtime: local function observe(...) calls += 1; return print(...) end
-- unluac-runtime: setfenv(run, setmetatable({ print = observe }, { __index = getfenv() }))
-- unluac-runtime: run()
-- unluac-runtime: assert(calls == 1)
print("observed")
```

观察代码在被测源码中始终是注释，不参与该模块的优化、局部槽或proto布局。尤其不能
把 `getfenv`/`setfenv` 观察器直接移入被测 Luau 模块：它们会改变整个模块的内联决策。
每个实例编译观察器一次。源码观察用官方CLI的loadstring按当前优化档加载原源码；
原chunk、生成chunk和每轮regen chunk由bytecode runner直接加载，作为唯一参数传给
同一观察器chunk。被测源码自身的编译指示保留，观察器不参与反编译或收敛比较。

普通独立运行仍执行；成功后另起进程做观察运行，两份完整stdout/stderr分别比较，
不拼接或跨运行抵消差异。观察失败保留失败退出状态及完整输出，归入当前执行阶段的
失败。观察器可以加强环境、求值次数、
根生命周期或调用层检查，不能代替原有运行及结构断言。产物目录额外保留
`runtime-observer`源码/chunk和`observed-source`入口，失败时可直接复现。
当前仅支持Luau普通Source expectation，其他方言/专用carrier协议不隐式复用此入口。
索引中使用`runtime-observer`交叉标签检索；可读性断言数量不计运行观察代码行。

## 可读性断言

可读性合同通过编译前解析的 `unluac:` 注释表达：

```lua
-- unluac: expect-contains [[local function test_assignment]]
-- unluac: expect-not-contains [[goto]]
-- unluac: expect-not-line [[local r0_2 = r0_1]]
-- unluac: expect-order [[if flag then]] [[else]]
-- unluac: expect-max-line-length [[120]]
-- unluac: expect-count [[local r1_0]] [[1]]
-- unluac: expect-min-count [[for ]] [[1]]
-- unluac: expect-max-count [[local r1_0]] [[2]]
-- unluac: expect-ast-min [[numeric-for]] [[1]] [[@proto=1]]
-- unluac: expect-ast-max [[empty-local]] [[0]] [[@debug=stripped]]
-- unluac: expect-name [[local:0]] [[arr]] [[@naming-mode=heuristic]] [[@debug=stripped]]
-- unluac: expect-count [=[["key"]]=] [[1]]
```

参数使用 Lua 长括号定界，支持 `[[...]]`、`[=[...]=]` 及更高等号层级；内容原样匹配。
片段含 `]]` 或以 `]` 结尾时使用更高层级，避免片段后缀与定界符提前闭合；不同参数可以使用不同层级。

`expect-not-contains` 匹配任意子串；禁止某一整行时使用 `expect-not-line`，比较时忽略行首缩进
和行末空白。例如禁止 `local x = y` 不会误伤 `local x = y()`，两种断言均用于首次生成及收敛轮次。

| 指令 | 含义 |
| --- | --- |
| `expect-contains` | 首次生成包含片段 |
| `expect-not-contains` | 首次生成和每轮 roundtrip 均不含片段 |
| `expect-order` | 首次生成中片段顺序固定 |
| `expect-max-line-length` | 首次生成和每轮 roundtrip 的物理行长度上限 |

### 出现次数与 AST 形状

文本出现次数使用不重叠子串计数，needle 不能为空；生成源码中的字符串与元信息注释也参与文本匹配。
需要忽略这些文本并检测语法节点时使用 AST 指标：

| 指令 | 含义与轮次 |
| --- | --- |
| `expect-count [[text]] [[N]]` | 首次生成中 `text` 恰好出现 N 次 |
| `expect-min-count [[text]] [[N]]` | 首次生成中至少出现 N 次 |
| `expect-max-count [[text]] [[N]]` | 首次生成及每轮 roundtrip 中至多出现 N 次 |

exact/min 是首次恢复源码的正向形状合同；roundtrip 可以把等价的 `break`、`while true` 等规范化成其他
写法，因此不要求保留首次的拼写。max 属于防止重复中转、膨胀或禁止形状回流的安全上限，必须每轮重验。

`expect-ast-count`、`expect-ast-min` 与 `expect-ast-max` 分别对最终 readability AST 的某项指标作恰好、
至少、至多约束。三者都只在首次生成的最终 AST 上执行，不在 roundtrip AST 上重算。可用 metric 为：

`empty-local`、`empty-function`、`local-decl`、`function`、`local-function`、`if`、`while`、`repeat`、
`numeric-for`、`generic-for`、`goto`、`label`、`break`、`continue`、`do-block`、`call`、`method-call`、`error`。

方言语法指标包括 `close-binding`、`global-decl`、`named-vararg-function`。
`close-binding` 按 local 声明中属性为 Close 的绑定计数；`global-decl` 按 global 声明语句计数，
不包含 `global function` 声明。`named-vararg-function` 统计拥有 named-vararg binding 的函数头，
与 `function` 一样归入包含该函数表达式/声明的父 proto，而不是函数自身的 body scope。
这些指标直接消费最终 AST 属性，不扫描字符串或元信息注释；存在数量也不能替代关闭顺序、
全局读写或变参别名的运行时观察。

表构造器指标包括 `table-constructor`、`table-list-field`、`table-record-field`：分别统计构造器表达式、
构造器内的数组字段和键值字段。嵌套 key/value 中的构造器照常遍历；构造之后的索引赋值不计入字段。
开放多返回尾表达式在语法上仍是一个数组字段，计数不代表运行时元素数。结合 proto 选择器可约束
初始化是否被拆成零散赋值，但表键身份、nil 槽、求值顺序和元方法仍须使用运行观察验证。

`function` 统计函数表达式或声明本身；`local-function` 只统计 local-function 声明；method call 同时计入
`call` 和 `method-call`。`empty-local` 指没有 values 的 local 声明，`empty-function` 指空函数体。不要把
`empty-local = 0` 当作通用“更可读”标准：它可能是 GC、Close、debug 窗口或物理 frame 的必要 carrier。

`repeat-condition-local` 是绑定关系指标：对每个 repeat，统计其 until 表达式读取的、
同时由该 repeat 直属 body 中有 RHS 的 local 声明引入的不同 binding 数量。同一 binding
多次读取只计一次；不计外层声明、嵌套块声明或条件表达式内 child function body 的引用。
例如 `repeat local done = step() until done` 计1，体内声明的 a、b 参与
`until a > 10 or b > 20` 计2；循环外的计数器不计入。身份消费最终 AST 的
`AstBindingRef`，与自动名称及其编号无关。指标不证明 initializer 的值域、运行路径
或一般等价性，仍须配合运行观察；需要特定运算或声明数量时保留相应独立断言。

### 命名断言

`expect-name [[local:0]] [[arr]]` 通过最终 AST 的 binding 身份查询 NameMap，精确比较名称，
不依赖生成文本。`local:N` 为所选函数中第 N 个可见局部声明（从 0 开始，按 AST 源码遍历顺序，
同一声明从左到右），包含 local function、numeric/generic-for 绑定及 SyntheticLocal，
不包含参数或子函数体。它不是 HIR LocalId；已消除的内部 local 不占序号。
`param:N` 和 `upvalue:N` 分别按参数、upvalue 槽位索引；省略 `@proto` 时检查入口函数。
目标函数、绑定或名称缺失均失败。不同方言可产生不同声明顺序，应按实际结构设置 selector。

命名断言只检查首次反编译，roundtrip 编译器可能重新分配绑定。用 `@naming-mode` 在同一源码中
区分三种模式的名称合同，manifest 必须注册相应 naming variant；仅写 selector 不会创建实例。
命名断言应搭配运行观察，防止一个看似合适的名称遮蔽全局或破坏 capture。

### 实例与 proto 选择器

任一指令可在数据参数之后追加零个或多个 `[[ @key=value ]]` 选择器（实际写法不含空格，如
`[[@dialect=lua5.4]]`）。同一指令的选择器采用 AND：指定的 dialect、debug、variant、naming-mode 必须同时匹配
manifest 展开的同一个实例。每种 selector 最多出现一次。

子 runner 的 `--list` 在输出实例列表之前，按源码路径读取一次断言并检查选择器覆盖。若某条断言
匹配不到该源码任何已注册配置，会携带路径、行号及选择器报错；错拼的 variant 不能静默跳过。
普通单实例执行不扫描其他源码。`@proto` 由匹配实例的最终 AST 检查，目标 proto 不存在也是失败。

| selector | 值 | 作用 |
| --- | --- | --- |
| `@dialect` | `lua5.1`、`lua5.2`、`lua5.3`、`lua5.4`、`lua5.5`、`luajit`、`luau` | 只对该方言实例执行 |
| `@debug` | `stripped`、`retained`、`ignored` | 只对对应 debug 策略执行 |
| `@variant` | manifest 的实际 variant label，或 `default` | 只对该 variant 执行 |
| `@naming-mode` | `debug-like`、`simple`、`heuristic` | 只对使用该命名模式的实例执行 |
| `@proto` | 非负 proto id | 用于 `expect-ast-*` 或 `expect-name`，选择该函数自身 |

debug 策略在每个实例中互斥：`ignore_debug` 优先为 `ignored`，否则 `retain_debug` 为 `retained`，其余为
`stripped`；一个指令不能同时匹配两种 debug 策略。`@proto` 的 id 是最终 AST 的 `HirProtoRef::index()`；
该 scope 不穿透子函数体。AST 计数未给 `@proto` 时统计整个模块，包含子函数；命名断言默认入口函数。
文本类指令不能使用 `@proto`。`@naming-mode` 使用实例实际选项，未显式配置时消费反编译默认值。
不同方言的 proto 编号可能不同，不能把某一编译器的声明顺序外推到其他方言；跨方言断言应选择
对应实例的 proto，或在目标结构全模块唯一时使用模块范围。

文本出现次数和 AST 指标只证明生成表示的局部形状，不能证明 Lua 运行语义、求值次数和顺序、元方法、
多返回宽度、物理 root 生命周期、GC、Close 或 debug 身份。涉及这些事实的 case 必须保留可观察的运行时
探针、方言/选项矩阵或已有专用合同；不可用“计数较小”替代等价证明。

正向形状断言不要求编译器 roundtrip 保留等价控制流的原始拼写。所有普通 case 在首次生成与每轮
roundtrip 都必须断言 `GeneratedChunkKind::Source`，诊断伪源码不能混入成功矩阵。

只接受 Strict 拒绝的专用 residual/island 合同，其 `unluac:` 断言检查首次 Permissive 诊断产物，
因此同样执行 contains/order、文本次数和 AST 形状断言。诊断模式不是 roundtrip，不能据此跳过
首次检查；其 AST 可以包含合同要求的 Error 节点。ProtoFailureRecovery 先运行原始 Source
样例并检查源码断言，随后注入的失败恢复结构由该专用合同检查，不将原源码形状要求套到注入结果。

## 新增测试

1. 先用 `--list` / `--list-json` 按主题、标签和保护边界检索；可承载新边界的已有源码优先扩展。
2. 新入口按所属主题和子主题分配下一个两位编号，并以具体标题说明输入结构；观察结果、求值次数、顺序或生命周期，必要时加稳定输出标签。
3. 依据目标结构补 `unluac:` 合同；允许更简洁的等价规约，但不以运行结果相同代替可读性证明。断言应定位独立子场景，不能在合并后由另一个子场景代为满足。
4. 新源码必须在对应主题 manifest 登记一次，填写标签、保护边界及完整配置；扩展已有源码时核对全部原配置仍适用，不以路径去重丢弃配置差异。
5. 先运行相关定向用例；同一完整主题集中修改、验证，共享测试协议变化收尾时运行一次 `cargo case-test --jobs 8`，不逐次编辑重复全量。

失败时先区分：源码/toolchain、parse/lowering、反编译、生成源码编译、运行输出、source kind、
收敛或可读性断言。用 `--stop-after` / `--dump-pass` 找到首次丢失事实的层，在根因 owner 修复。
调试命令见 `10.debugging.md`。

Lua toolchain 位于 `lua/build/`，源码与构建说明见 `lua/README.md`。
